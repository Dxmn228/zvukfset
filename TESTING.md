# Тесты проекта

## Серверные проверки

Из корня проекта, после активации окружения:

```bash
python -m pytest -c pytest.ini --ds=zvukfest.settings_ui -p no:cacheprovider -q
```

Используется временная SQLite. Проверяются:

- регистрация прямыми запросами: email, дубликаты, пароль, обязательные галочки;
- смена пароля, сохранение текущей сессии и прекращение других сеансов;
- защита приватных API, изоляция профилей, обращений, действий, корзин и заказов;
- CSRF: отклонение записи без корректного токена и успешная запись с ним;
- вход, выход, истечение сессии, «Запомнить меня», обновление `last_login`;
- валидация обращений, поиск и ограничение истории последними пятью записями;
- админка: роли, CRUD товаров и категорий, свойства и изображения, скидки,
  поиск, сортировка, фильтры, редактирование пользователей и модерация;
- ограничения БД и откат заказа при искусственно вызванной ошибке записи.

Пять PostgreSQL-сценариев в этом запуске помечаются `SKIPPED` намеренно.

## PostgreSQL и перезапуск базы

Нужны работающий Docker Desktop и локальный образ `postgres:17`.
Если образ ещё не скачан, выполните `docker pull postgres:17`.

```bash
python scripts/run_postgres_tests.py
```

Скрипт запускает весь серверный набор на отдельном PostgreSQL через
`compose.test.yaml`. У тестового проекта уникальное имя `zvukfest-test-…`,
отдельный том и свободный порт. Рабочие `compose.yaml`, `.env` и база сайта
не используются. После завершения тестовые контейнер и том удаляются.

Дополнительные сценарии проверяют миграцию с сохранением старых записей,
внешние ключи, два одновременных оформления с одинаковыми и разными
идентификаторами запроса, сохранность пользователя, сессии, корзины и заказа
после перезапуска **только тестового** PostgreSQL-контейнера.
Тест перезапуска сверяет Compose-метки контейнера перед действием.

Для отдельной проверки можно передать фильтр pytest:

```bash
python scripts/run_postgres_tests.py -k simultaneous
```

Скрипт сам применяет миграции к тестовой базе. Не запускайте тесты миграций
или перезапуска с рабочими настройками подключения.

## Тесты интерфейса

Браузерные тесты запускаются через pytest и Playwright в Chromium и Firefox.
Они открывают настоящий Django-сервер на свободном локальном порту и работают
с временной тестовой базой SQLite. Docker, PostgreSQL и рабочий сайт запускать
не нужно. Секреты из `.env` не читаются; данные сайта не изменяются.

## Установка

Команды ниже выполняются **из корня репозитория**, где находится `compose.yaml`.
Для Git Bash:

```bash
source zvukfest/zvukfest/.venv313/Scripts/activate
python -m pip install -r zvukfest/zvukfest/requirements-test.txt
python -m playwright install chromium firefox
```

Для PowerShell команда активации:

```powershell
./zvukfest/zvukfest/.venv313/Scripts/Activate.ps1
```

## Запуск

```bash
python -m pytest -c pytest.ui.ini -v
```

Если терминал открыт в папке с `manage.py`, путь к конфигурации другой:

```bash
python -m pytest -c ../../pytest.ui.ini -v
```

Посмотреть действия в окнах браузеров:

```bash
python -m pytest -c pytest.ui.ini --headed --slowmo 200 -v
```

Запустить только проверки корзины:

```bash
python -m pytest -c pytest.ui.ini -k cart -v
```

Проверить список сценариев без запуска браузеров:

```bash
python -m pytest -c pytest.ui.ini --collect-only -q
```

## Что проверяется

- Навигация по страницам, одинаковое меню, доступность ссылки «Билеты» в корзине.
- Переход гостя из личного кабинета на вход и состояние корзины для гостя.
- Мобильное меню: клавиши Tab, Enter, Escape, видимый фокус и размер кнопки.
- Отображение билетов, корзины, профиля и политики при ширине 360, 768 и 1440 px.
- Регистрация и ссылки на документы в новых вкладках без потери введённых данных.
- Обязательные галочки, несовпадающие пароли и некорректный email.
- Ошибка входа, редактирование профиля, сохранение изменений и выход.
- Сообщение об ошибке сети в личном кабинете и восстановление после перезагрузки.
- Отправка обращения и очистка формы после успешной отправки.
- Поиск билетов, пустой результат, недоступность распроданного билета.
- Повторная загрузка каталога после ошибки сервера.
- Добавление, изменение количества, пересчёт суммы, удаление и очистка корзины.
- Сохранение корзины после обновления страницы и восстановление кнопок после ошибки.
- Слайдер: три слайда, циклическое переключение кнопками и клавиатурой.
- Скачивание политики, описание билета и история просмотров.
- Всплывающая корзина, счётчик, скидки и очистка localStorage при выходе.
- Учебный заказ: оформление, очистка корзины и сохранение истории после обновления.
- Смена пароля: ошибки, успешная смена, отказ старого пароля и вход с новым.
- Сохранённый HTML в билете и обращении отображается текстом, не выполняет JavaScript.

Проверки `tests/test_orders.py` дополнительно проверяют округление скидок,
фиксацию цен заказа, повторную отправку без дубликатов, изменение цены перед
оформлением, изоляцию аккаунтов, состав корзины в сессии и недопустимые количества.
Для запуска всех backend-тестов на временной SQLite без рабочей базы:

```bash
python -m pytest -c pytest.ini --ds=zvukfest.settings_ui -p no:cacheprovider -q
```

После обновления проекта примените миграции из каталога с `manage.py`:

```bash
python manage.py migrate
```

При запуске через Compose из корня проекта используйте `docker compose up -d --build`:
команда запуска backend уже выполняет миграции. Скидка задаётся в админке товара
(0–100%, по умолчанию 0). Заказы учебные; реальные платежи не выполняются.

На каждой странице проверяются необработанные ошибки JavaScript и ошибки
загрузки локальных CSS, JS и изображений. Внешняя карта подменяется пустой
страницей: доступность OpenStreetMap не является предметом этих тестов.
В трёх сценариях ошибки API создаются намеренно; остальные обращения идут
к настоящему тестовому Django-серверу.

Файлы `ui_*.py` собираются отдельной конфигурацией `pytest.ui.ini` и не входят
в обычный запуск backend-тестов `test_*.py`. Показатель покрытия Python из
обычного запуска не заменяет эти браузерные проверки. SQLite в UI-тестах также
не заменяет отдельные проверки PostgreSQL и миграций.

## Результаты

Скриншоты адаптивности: `artifacts/ui/layouts/<браузер>/`.
При падении теста Playwright сохраняет скриншот и `trace.zip` в `artifacts/ui/`.
Пути отсчитываются от папки, из которой запущена команда.

Открыть трассировку конкретного теста:

```bash
python -m playwright show-trace "путь/к/trace.zip"
```

Для отчёта можно сохранить результат в XML:

```bash
python -m pytest -c pytest.ui.ini -v --junitxml=artifacts/ui-results.xml
```

Артефакты исключены из Git и Docker-сборки. Файл `settings_ui.py` предназначен
только для тестов и не должен использоваться для запуска публичного сайта.

Документация: [Playwright для pytest](https://playwright.dev/python/docs/test-runners),
[тестовый сервер pytest-django](https://pytest-django.readthedocs.io/en/latest/helpers.html#live-server).

## Проверки опубликованного сайта

Команды выполняются из корня репозитория в активированном окружении.
Отдельная конфигурация `pytest.hosting.ini` не загружает Django, `.env` или
локальную базу данных. Обычные backend- и UI-тесты не обращаются к хостингу.

Проверки HTTP, DNS, сертификата, редиректа HTTP → HTTPS, страниц, минимум
10 внутренних ссылок с якорями, ресурсов и стилей админки, подключения backend
к базе, каталога, поиска, скачивания политики, защиты приватного API, CSRF,
cookie, служебных файлов и отсутствия публичной отладки:

```bash
python -m pytest -c pytest.hosting.ini --hosting-url=https://zvukfest.de3.netrun.io -m "not browser and not writes" -v --junitxml=artifacts/hosting/http-results.xml
```

Первый запрос допускает пробуждение сайта до 60 секунд; обычные запросы имеют
таймаут 20 секунд. Ошибка подключения означает невозможность проверки, а не
доказательство ошибки приложения. HTTPS-сертификаты всегда проверяются.

Проверки в Chromium и Firefox с реальными ресурсами хостинга: страницы, ошибки
JavaScript, загрузка ресурсов, mixed content, каталог, ссылки на документы,
валидация формы, базовые проверки доступности и клавиатуры, адаптивность
360/768/1440 px, время загрузки главной страницы до 3 секунд после пробуждения:

```bash
python -m pytest -c pytest.hosting.ini --hosting-url=https://zvukfest.de3.netrun.io --hosting-browser --browser chromium --browser firefox -m browser -v --junitxml=artifacts/hosting/browser-results.xml
```

Нужны браузеры, установленные через `python -m playwright install chromium firefox`.
Chromium — движок Chrome; для проверки именно установленного Google Chrome
можно отдельно использовать `--browser chromium --browser-channel chrome`.
Скриншоты адаптивности сохраняются в `artifacts/hosting/layouts/`.
Не включайте запись трассировок при использовании реального аккаунта администратора.
Проверка входа в админку пропускается без переменных окружения
`HOSTING_ADMIN_EMAIL` и `HOSTING_ADMIN_PASSWORD`. При их наличии открывается
форма добавления товара, но товар не сохраняется. Пароль не записывайте в Git.

Полный сценарий с записью данных запускается отдельно:

```bash
python -m pytest -c pytest.hosting.ini --hosting-url=https://zvukfest.de3.netrun.io --hosting-writes -m writes -v --junitxml=artifacts/hosting/journey-results.xml
```

Он создаёт нового пользователя `hosting-test-…@example.invalid`, изменяет его
профиль, отправляет тестовое обращение, проверяет сохранение и очистку корзины,
создаёт один учебный заказ, повторяет запрос без дублирования, выходит и входит
заново для проверки истории. Требуется хотя бы один доступный билет. Реальных
платежей нет. Данные этого теста остаются в базе: email и номер заказа записаны
в XML для последующей ручной очистки через админку. Другие аккаунты и их корзины
тест не использует. Проверка сохранения между запросами не доказывает
сохранность данных после перезапуска контейнеров или повторного деплоя.

`SKIPPED` означает, что сценарий не выполнялся; это не успешный результат.
Ошибки проверок Secure-cookie или DEBUG нужно исправлять в конфигурации
публикации. Не отключайте проверки ради зелёного отчёта. При выключении DEBUG
также необходимо обеспечить раздачу статики админки.

## Нагрузка на хостинг

Скрипт отправляет ровно 100 GET-запросов к главной странице за один прогон;
перед ними выполняется один отдельный запрос для пробуждения приложения.
Параллельность задаётся явно. Сначала выполните первый этап; при ошибках
подключения или HTTP не повышайте нагрузку до устранения причины.

```bash
python scripts/run_hosting_load.py --url https://zvukfest.de3.netrun.io --concurrency 10
python scripts/run_hosting_load.py --url https://zvukfest.de3.netrun.io --concurrency 50
```

Результаты: `artifacts/hosting/load-c10.json` и `load-c50.json`.
Повторный прогон перезаписывает соответствующий файл; для сохранения предыдущего
отчёта укажите другой путь через `--output`.
Сохраняются число успешных и ошибочных запросов, HTTP-статусы, среднее время,
p95 (95% запросов уложились в это время), RPS и длительность прогона.
Время включает сеть, TLS и получение HTML. Подготовка клиентов и загрузка
хранилища сертификатов вынесены за пределы измерения. Статика и JavaScript
при нагрузочном прогоне не загружаются; подключение создаётся для каждого запроса.
Цель из примера лабораторной: ноль ошибок и p95 не выше 500 мс. При нарушении
порога отчёт всё равно сохраняется, а команда возвращает код 1. Другой порог
можно явно задать через `--p95-ms`, но для отчёта нужно указать его изменение.

Это короткое сравнение двух уровней параллельности, а не определение предельного
числа пользователей. Оно не измеряет CPU/RAM контейнеров, длительную устойчивость
или производительность регистрации и оформления заказа. Для этих выводов нужны
дополнительные длительные сценарии и графики вкладки «Мониторинг» хостинга.

## Дополнительные материалы для лабораторного отчёта

Автоматические проверки выше не заменяют требуемые лабораторной отчёты WAVE
и Lighthouse. Для опубликованного URL сохраните результаты WAVE и Chrome
DevTools → Lighthouse (Navigation; Performance, Accessibility, Best Practices,
SEO). Цели: Accessibility ≥ 90, Performance ≥ 80. Проверьте контраст, порядок
заголовков и удобство элементов на снимках 360/768/1440 px. Базовая проверка
меток и фокуса в pytest не является полным аудитом доступности.

Проверка восстановления из резервной копии, сохранности данных при деплое,
логов запуска и фактического применения миграций требует доступа к панели
хостинга и отдельной копии базы. Публичные HTTP-тесты не перезапускают рабочие
сервисы и не восстанавливают рабочую базу. Для отчёта эти проверки следует
отмечать отдельно, а не считать выполненными по результату `/api/health`.
